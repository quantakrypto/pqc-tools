# pqc-tools roadmap — toward 1.0

_Last reconciled 2026-08-05 against the 0.9.0 line. This supersedes the older
audit backlogs: every P0/P1 item they tracked has shipped. What remains is
nice-to-have accuracy, an architecture keystone, perf, and test-hardening — the
list a pre-1.0 project keeps to earn a stable API promise._

## Remaining toward 1.0

Checkboxes are the live list. Sizes: **S** ≈ an afternoon, **M** ≈ a few days,
**L** ≈ a real project. Every change must keep the benchmark at F1 = 1.000 and
pass `npm run build && npm test && npm run lint && npm run format:check`.

### Detection accuracy
- [x] **PHP `composer.json` dependency scanning** (S) — a whole ecosystem
  (phpseclib, paragonie/*, Tink-PHP) was invisible; added `composer` to the
  ecosystem union + a small curated DB. `dependencies.ts` `manifestEcosystem`/
  `candidateNames`/`vulnerableDependencies`. _Shipped in 0.6.0._
- [ ] **Deny-list & call-syntax FP suppression** (M) — a `["RS256", ...]` reject
  list, or a crypto call named inside a log string, still produces findings that
  dent the readiness score. Extend `CODE_ONLY_RULES` / `stripStringLiteralFindings`
  and add allow/deny-array awareness to `RE_JWT_ALG`.
- [x] **JS home-turf hardening** (M) — variable-typed `generateKeyPair(kind, …)`,
  `crypto['createSign']` computed-member access, wider node-forge than
  `pki.rsa`/`ed25519`. The home language should be airtight. _Shipped._
- [x] **package-lock v1 nested tree + `npm:` alias resolution** (S–M) — transitive
  vulnerable deps in legacy lockfiles and aliased packages were silently missed
  (`scanNpmManifest` only walked top-level keys + the flat v2/v3 `packages` map).
  _Shipped in 0.6.0._

### Compliance / mandate enforcement
The dated `--mandate` gate (cnsa-2.0 / nist-ir-8547), its `--policy` composition,
and machine-readable JSON/SARIF/evidence output shipped across 0.8–0.9; CNSA 2.0
now carries its own 2030/2033 timeline (distinct from IR 8547's 2035). What's open:
- [ ] **CNSA 2.0 parameter-level policy** (M) — the dated, *family*-level gate
  exists; the open half is a check that flags a sub-CNSA PQC choice already in the
  code (e.g. ML-KEM-768 where CNSA 2.0 requires 1024), so a "CNSA readiness" claim
  is end-to-end pass/fail on the PQC side too, not just on retiring classical PKC.
- [ ] **Additional mandate regimes** (M) — DORA / NIS2 / PCI DSS as first-class
  `--mandate` ids. They currently inherit the CNSA 2.0 / IR 8547 timelines and are
  cited only in docs; a first-class catalog entry gives each its own citation and
  any independent algorithm date.
- [ ] **Per-system-class CNSA waves** (S) — optionally encode CNSA 2.0's staggered
  exclusive-use dates (2030 software/firmware signing, 2033 general NSS) selectable
  by system type, rather than the single 2033 disallow the `cnsa-2.0` clause uses.
- [ ] **Per-result mandate annotations in SARIF** (S) — surface each verdict on its
  own code-scanning alert, not only the run-level `properties.mandate` summary.

### Architecture / DX
- [ ] **Declarative detector factory `defineRegexDetector({id,language,scope,extensions,rules})`** (L)
  — the highest-leverage item. Today any custom detector forces the whole scan
  onto the serial path (`parallel.ts` rejects non-cloneable detectors; the worker
  rebuilds only `defaultRegistry`). A data-only factory makes detectors
  structured-cloneable and lets third parties ship rule packs.
- [ ] **Pluggable dependency ecosystems + JSON vuln DB** (L) — the 90-entry inline
  TS array and hand-maintained `candidateNames` switch don't scale; a JSON DB is
  also externally auditable and updatable without a release.

### Performance
- [ ] **Throughput + memory-safety pass** (M, each sub-item S) — a per-scope keyword
  prefilter (today every detector runs on every file), ~~eliminate the parallel-path
  double-stat~~ (_shipped: `walkFilesSized`_), ~~a manifest size-cap~~ (_shipped_),
  and retry a failed worker chunk once instead of a full serial re-scan.

### Tests
- [ ] **Golden-file output snapshots + a vendored-OSS corpus** (M–L) — locks scan
  output against regressions the labeled precision/recall corpus can't catch;
  real-repo sweeps are ad-hoc today.

### Deliberate non-goals / tradeoffs
- **Bidirectional WebCrypto proximity** is one-sided *by design* (`nearSortedCall`
  looks backwards only) — a documented false-positive tradeoff. Revisit only with
  a corpus proving a net recall gain, not as a straight fix.
- **Merging `core.formatSummary` and `qscan.renderHuman`** — deliberately kept
  separate; they are genuinely different surfaces (terse machine vs. rich banner).

## Distribution / ecosystem (non-code)

Awesome-list, registry, and directory placements are tracked in the internal CRM
(`crm_item kind='listing'`). Highest-leverage open submissions:
`sobolevn/awesome-cryptography` (7k★, has a PQC section) for reach, and
`bro256/Awesome-PQC-Resources` for dedicated PQC. Our PR to
`veorq/awesome-post-quantum` (the canonical dedicated list) was not accepted.

## The 1.0 gate

1.0 is an API-stability promise, not a feature count. The blockers are: the
declarative detector factory (so the plugin surface is stable), the JSON vuln DB
(so data updates don't need a release), and the golden-file corpus (so the frozen
API is regression-locked). Everything else above can ship in 0.x point releases.
